Case study · Maxtel

Sales ingest for a 180-store fast-food franchise group in New Zealand

Every night each store's point-of-sale system sends its sales, and by morning every one of them has to be in the ledger. I moved that ingest off a synchronous request path onto S3, SQS FIFO and autoscaled Fargate workers, then load-tested it until it held at 180 stores.

ClientA fast-food franchise group in New Zealand, rolling out to 180 stores
EmployerMaxtel, as a contract software engineer
ProductAn AWS and TypeScript platform replacing a legacy low-code back office for the franchises
How I built itWith Claude Code agents, working from a spec, a plan and tests. I reviewed every change before it merged.

Problem

Store sales arrive as XML bundles. The old path parsed each bundle inside the HTTP request, in a single 930-line database transaction. It managed 3.75 bundles a minute, which was too slow for a 180-store rollout, and long requests were timing out at the load balancer. Two pushes for neighbouring days from the same store could also race each other, which left some sales days silently underived.

Constraints

  • No store-day can go missing. Sales feed stock, costing and the reports sent back to the franchisor.
  • Bundles from one store have to be processed in order, while different stores can run in parallel.
  • The ledger is a shared multi-tenant Postgres database with row-level security, so heavy locking hurts every tenant.
  • The rollout goes tenant by tenant behind a feature flag, and the new path had to be proven under a full-size load test before any of that.

Architecture

What I did

I re-architected the accept path so it does very little. It writes the raw bundle to S3, records a pending row, and sends one SQS FIFO message keyed by store. A pool of autoscaled Fargate workers picks up the messages, claims the row, parses the XML and derives the ledger events. A scheduled EventBridge sweep catches any sales day that didn't complete, and support staff get a console to replay a failed ingest without engineering help.

The first 180-store load test failed. p99 accept latency was 13.3s. I worked through the CloudWatch metrics and found three root causes. S3 writes were happening inside a locked database transaction. A version check parsed the whole XML file just to read one attribute. And the autoscaler was scaling in workers that were still busy. I moved the S3 writes out of the lock, replaced the full parse with a root-tag scan (507ms to 10ms at p50), and stopped busy workers from being scaled in. Together that cut p99 accept latency 8x.

Afterwards I extracted the reusable CDK constructs and the async-ingest runtime into shared npm packages and moved consumers across 4 repositories onto them. Synth-diffing 14 stack and environment pairs showed zero infrastructure drift.
